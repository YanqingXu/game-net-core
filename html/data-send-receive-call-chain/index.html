调用链总览

game-net-core 为游戏服务端提供 C++23 网络基础设施。客户端和服务端建连后都由 TcpConnection 收发数据，连接所属的 EventLoop 派发内核通知并执行应用回调。

接收 · 从内核到应用

Linux epoll

收到就绪事件后读取

  1. epoll_wait() 返回读就绪端口校验当前注册代号。
  2. Channel 派发读回调连接所属线程进入 handleRead()。
  3. readv() 读取字节按剩余输入额度追加到 inputBuffer_。
  4. MessageCallback 消费输入回调返回后复查未消费字节数。

Windows IOCP

先提交操作，再消费完成通知

  1. startRead() 提交 WSARecv()为在途操作保留连接私有读区。
  2. 所属线程收到完成通知按操作身份和观察者代号派发。
  3. completeRead() 取出字节把本次完成字节追加到 inputBuffer_。
  4. MessageCallback 消费输入返回后复查关闭、额度和读许可，再决定续投。

发送 · 从应用到内核

Linux epoll

先尝试直写，可写后继续排空

  1. trySend() 预留额度跨线程调用复制负载并投递到所属线程。
  2. 符合直写条件时调用 send()已有待写输出时，将新字节追加到队尾。
  3. EPOLLOUT 触发缓冲续写未写完的字节保存在 outputBuffer_。
  4. 结算已写字节按实际写入量释放额度，排空后关闭写兴趣。

Windows IOCP

字符串段入队，由完成通知推进

  1. trySend() 预留额度跨线程调用复制负载并投递到所属线程。
  2. startWrite() 提交 WSASend()操作借用队首字符串段的当前偏移。
  3. completeWrite() 推进偏移按完成量消耗段，整段消费后才能出队。
  4. 结算或继续提交释放本次完成额度，剩余字节从新偏移续投。

建连与线程归属

  1. 服务端启动。 应用创建 base loop 和 TcpServer，先配置连接与消息回调，再调用 start() 启动线程池并让 Acceptor::listen() 注册监听。监听就绪后，Linux 的 Socket::accept() 使用 accept4() 取得非阻塞 socket。Windows 通过预投递的 AcceptEx 完成通知交付新 socket。
  2. 服务端分配所属线程。 TcpServer::newConnection() 在 base loop 做准入、挑选连接的 I/O loop 并维护 connections_。零 worker 时用 base loop，有 worker 时按线程池策略选取。服务端把回调配置和建连任务投递到选定 loop，任务接受后由该线程调用 connectEstablished()。
  3. 客户端主动连接。 TcpClient 通过 Connector 发起连接。Linux 在连接中的 socket 可写时检查 SO_ERROR，Windows 消费 ConnectEx 完成并在交接中保留同一 loop 的 IOCP 关联。成功后 TcpClient::newConnection() 在自己的 loop 上构造、配置并建立 TcpConnection。
  4. 激活连接。 connectEstablished() 绑定 Channel::tie()、开启读兴趣、挂接 lifecycle 节点并设为 kConnected。Windows 在连接回调前提交首次 WSARecv()，Linux 随后在读就绪时取数据。成功进入这一阶段后，已连接回调可以在所属线程同步发出第一笔数据。

一条连接的状态、缓冲区和用户回调归属同一个 EventLoop。 监听和服务端连接表归 base loop，连接 I/O 归选定的 loop。TcpConnection 管理 socket 和 Channel，Channel 保存回调和事件兴趣，EventLoop 管理后端注册与派发。

正常轮次在已有 I/O 批次耗尽后等待新事件，按预算派发 I/O，再处理到期定时器、控制源、lifecycle 节点和普通任务。maxActiveChannelsPerIteration 限制单轮 I/O 派发，后端取事件的批大小由各自配置控制。

发送入口与准入

  1. 检查调用和连接状态。 send() 调用 trySend() 并丢弃返回值。trySend() 先检查关闭封口，再判断连接状态。连接可发送时，零字节请求直接返回 Accepted，无需启动写操作或安排写完成回调。长度大于零的指针调用要求可读数据，空指针会触发参数异常。
  2. 先预留输出额度。 tryReserveOutputBytes() 依次尝试连接、所属 loop、服务端、可选共享全局预算。后一级拒绝时回滚之前的额度。服务端在建连时注入 loop 和 server 预算，连接本身始终执行单连接限制。
  3. 在所属线程执行。 同线程直接进入 sendReservedInLoop()。Linux 直接写时可借用传入字节，需要缓冲时保存余量。Windows 创建拥有字节的字符串，随后移入段队列。
  4. 跨线程复制后投递。 先复制字节，再用 EventLoopExecutor::post() 把字符串与 TcpConnectionPtr 一起移交给普通任务队列。成功入队会唤醒线程，Linux 通过 eventfd，Windows 通过唤醒完成包。队列拒绝以及任务执行前连接已经完全关闭时，都会回收额度。已经准入的任务可以在 kDisconnecting 期间继续写出。
TcpSendResult出现位置
Accepted本地已接收请求，随后通过直接写、待写队列或关闭清理结算字节。
Closed连接当前无法发送，或关闭请求已封住新输出。
Overloaded、LoopOverloaded、ServerOverloaded、GlobalOverloaded相应的输出预算拒绝本次预留。
SchedulingQueueFull、OwnerShutdown、OwnerUnavailable跨线程投递被普通任务队列或执行器拒绝，分别对应 QueueFull、Shutdown、OwnerUnavailable。

Linux · epoll 就绪路径

默认生产 EventLoop 通过私有 PollerIoEngineAdapter 使用 EpollReadinessPort。端口拥有 epoll fd、唤醒 eventfd、注册和事件批次。内核事件携带注册代号，端口校验其与当前 fd 的绑定并丢弃过期事件。当前使用水平触发，只要 fd 仍就绪，就可以在后续轮次继续分配到读写处理。

接收 · EPOLLIN → readv → MessageCallback

  1. EpollReadinessPort::wait() 调用 epoll_wait()。端口把原生事件转换为就绪掩码，adapter 调用 Channel::setRevents() 记录返回事件，再把 Channel 加进本轮待派发列表。
  2. EventLoop::dispatchActiveChannels() 调用 Channel::handleEvent()。关联对象通过 tie() 临时保活，读事件沿构造时绑定的回调进入 TcpConnection::handleRead()。
  3. handleRead() 计算输入剩余额度，并调用 inputBuffer_.readFd(fd, &err, remaining)。Buffer::readFd() 用一次 readv() 先填 Buffer 可写区，最多再填 64 KiB 栈临时区。返回后推进写索引，只有落在临时区的字节需要再追加到 Buffer。
  4. 有新字节且读处于启用态时，调用 messageCallback_(shared_from_this(), &inputBuffer_)。回调看到此前尚未消费的字节与新字节，按协议推进读索引。回调返回后检查未消费输入是否达到上限。
  5. 读到 0 进入 PeerEof 关闭路径。EAGAIN、EWOULDBLOCK 或 EINTR 结束这次处理。致命读取错误进入 handleError()。

发送 · 直接写与 EPOLLOUT 续写

  1. sendReservedInLoop() 在 outputBuffer_ 为空且未关注写事件时，先走 sockets::write()，Linux 最终调用 send(fd, data, len, MSG_NOSIGNAL)。立即结算内核接受的字节。全部写完时尝试排入写完成通知。
  2. 遇到部分写、暂时不可写或中断时，将余量追加到 outputBuffer_。如果已有待写字节，则直接把新数据排在其后。检查读反压，随后开启 Channel 写兴趣，对应 epoll 的 EPOLLOUT。
  3. 可写后，Channel 把控制权交给 TcpConnection::handleWrite()。它通过 outputBuffer_.writeFd() 发送从 peek() 起的未消费字节，按实际写入量 retrieve(n)、释放输出额度并重新判断反压。内核暂时接收不了更多字节时，保留剩余数据和写兴趣。
  4. 缓冲区排空后关闭写兴趣。如果正在优雅关闭，先检查半关闭条件，再尝试排入写完成通知。致命写错误进入统一关闭，由关闭流程清理未发余量。

同一就绪事件可以包含多种信号。 EPOLLRDHUP 与 EPOLLHUP 映射为关闭信号。Channel::handleEventWithGuard() 的顺序为关闭信号（没有同时置读位时）、错误、读、写。前一个回调如果移除了注册，代号会变化，当前分发会跳过其余回调。移除其他活动 Channel 时，EventLoop 也会让它在本批的位置失效。

Windows · IOCP 完成路径

IocpPoller 将 socket 关联到所属 loop 的完成端口。Channel 提供连接观察者身份，IocpTcpTransport 提供稳定的 OVERLAPPED、读存储和写数据段。读写回调由有类型的完成通知直接触达 transport consumer。

  1. 调用 WSARecv() 或 WSASend() 前准备 IocpOperation。立即成功和 WSA_IO_PENDING 都提交完成义务，并让 poller 持有对应的 transport 存储。其他同步错误走拒绝与 handleError()，无需等待这一操作的完成包。
  2. IocpPoller::waitNativeCompletionNotices() 调用 GetQueuedCompletionStatusEx()，过滤唤醒包和无效操作，记录字节数/错误，终结内核操作代号并将存储租约转交给本批 CompletionNotice。短暂保留的 consumer 完成状态阻止同一操作在通知消费前复用。
  3. EventLoop::dispatchActiveChannels() 校验通知冻结的 fd、Channel 和注册代号。身份有效时在 tie() 保活下进入读写处理。身份已撤销时，私有 consumer 只推进关闭和终结结算。批次消费完后释放相应存储租约。

接收 · startRead → WSARecv → completeRead

connectEstablished() 或前次读完成后调用 startRead(remainingInputCapacity())。同一连接最多一笔未消费的读操作，按需分配并复用连接私有读区，每次最多提交 min(4 KiB, 剩余输入额度)。完成进入 handleRead()，由 completeRead() 将有效字节追加到 inputBuffer_。随后按当前读状态交付 MessageCallback，再检查连接、关闭、输入额度与反压状态，决定是否续投。

暂停读取期间，已经提交的读仍可能完成，字节可暂存于 inputBuffer_。输出降至低水位时，resumeWindowsReadAfterBackpressure() 先交付已缓冲数据，回调返回后复查是否已关闭、是否仍允许读，再在需要时提交下一笔 WSARecv()。零字节完成进入 EOF 路径。

发送 · enqueueWrite → WSASend → completeWrite

  1. sendReservedInLoop() 把持有字节的字符串移动到 writeSegments 队尾，更新缓冲计数并检查读反压。没有未完成的写时，startWrite() 让 WSABUF 指向队首字符串从 offset 起的一段内存，提交 WSASend()。
  2. 写完成通知进入 handleWrite()。completeWrite() 校验完成量并推进队首偏移及缓冲计数，完整消费的段才出队。连接按完成字节释放预留，部分完成时下一次从新的偏移续投。有效的非空提交若收到零字节写完成，按 WSAECONNRESET 进入错误处理。
  3. 反压恢复可能同步进入消息回调，回调可再次发送或关闭。因此外层 handleWrite() 复查关闭状态和在途写，随后启动下一笔写或在队列清空时关闭写状态、处理待定半关闭并安排写完成通知。

缓冲区与反压

位置归属和用途
inputBuffer_连接所属线程持有的未消费 TCP 字节。peek() 可查看，retrieve(n) 消费前缀，retrieveAllAsString() 复制并消费当前可读区。Buffer* 只在消息回调期间借用，应用需跨回调或跨线程使用时，先复制所需字节。
平台待写数据Linux 的 outputBuffer_ 保存未写出的连续字节。Windows 的 writeSegments 保存包括在途写在内的剩余字节，每段用独立偏移追踪进度。两边都只在所属线程推进数据。
pendingOutputBytes()可跨线程读取的预留字节快照，覆盖平台待写字节以及已通过预留但还留在跨线程投递中的字节。实际写出、排队拒绝、关闭丢弃都会按对应字节数回收。
内核 socket 缓冲区操作系统管理。Linux 系统调用返回或 Windows 写操作完成时，连接可以结算相应的本地输出额度。远端收取和处理数据发生在独立的链路阶段。

三种输出阈值各管一件事

  • 硬上限控制新发送。 hardLimitBytes 用于连接额度预留，默认 16 MiB。因超额拒绝进入过载后，预留字节数降至低水位或以下时恢复。连接以上的 loop、server 和可选 global 预算也各自执行容量限制与恢复阈值。
  • 读反压由实际待写字节触发。 待写数据达到 highWaterMarkBytes 时暂停读，降到 lowWaterMarkBytes 或以下时恢复。默认高、低水位分别为 4 MiB、2 MiB。Linux 更新读兴趣，Windows 还需安排真正的读操作。
  • 高水位回调提供通知。 setHighWaterMarkCallback() 设置独立阈值。待写字节从阈值下方跨至阈值时，连接尝试把该回调放进普通队列。WriteCompleteCallback 同样延后执行。可选通知入队失败时累计 droppedNotificationCount()，读反压和发送进度由各自的同步状态转换继续推进。

未消费输入有独立上限。 maxInputBufferBytes 默认 2 MiB。每次读的提交量受剩余额度约束，有新输入时让应用先消费，达到上限且仍未消费掉足够字节时以 InputLimit 关闭。业务帧最大长度和积压策略需要与这一额度配合。

关闭与回调顺序

优雅关闭先让本地输出结算

  1. tryShutdown() 封住新输出，发布 GracefulShutdown，让所属线程推进 kDisconnecting。跨线程请求通过建连时挂接的 lifecycle 节点唤醒处理，普通发送任务队列的容量与该通知路径独立。
  2. shutdownInLoop() 等待关闭请求有效、socket 仍开着、写兴趣已关闭且 pendingOutputBytes() == 0。此时调用 Socket::shutdownWrite()，Linux 对应 SHUT_WR，Windows 对应 SD_SEND。已经准入但尚未执行的发送仍占用预留，因此仅看到待写缓冲区为空还需要继续核对预留字节数。
  3. 最后一份预留释放时会唤醒 lifecycle 节点，覆盖直接写完成和生产线程投递回滚的情况。半关闭后仍可处理入站数据，连接最终在对端 EOF、错误或强制关闭路径结算。

强制关闭、EOF 和错误汇合

  1. tryForceClose() 请求立即关闭，handleRead() 的零值和 handleError() 也会进入统一清理。closeInfo() 保留首先发布的语义原因，后续 I/O 错误可以补上原先为零的 nativeError。典型原因包括 PeerEof、Reset、InputLimit、ForcedShutdown 和 CallbackFailure。
  2. beginCloseInLoop() 在所属线程撤销 Channel 注册后关闭 socket。Windows 若有未结算操作，先请求 CancelIoEx()，保存连接保活引用，并在 socket 关闭后以 CompletionDraining 状态等待终结通知。通知仍要由私有 consumer 结算，之后才可释放操作借用的读区或字符串。
  3. finishClose() 置 kDisconnected、清理待写数据并发布 Closed 阶段。正常回调顺序为断开状态的 ConnectionCallback → CloseInfoCallback → 内部 CloseCallback。服务端随后在 base loop 移除连接表记录并把 connectDestroyed() 投递回 I/O loop。客户端在自己的 loop 移除连接并直接调用 connectDestroyed()，再按请求与重试配置决定是否发起新连接。

回调里的重入会改变后续执行条件。 建连、消息、写完成和高水位回调可以调用发送或关闭。其异常被观测并使该连接进入关闭。断开、关闭观察回调的异常由框架记录，清理继续收敛。EventLoop::quit() 之后仍会排空已接受的任务和后端完成义务，经过 Quiescing、FinalDraining 后才发布 Shutdown。

走读 Echo 与拆帧

跟踪一条 ping 的往返

使用已构建的示例时，先启动 echo_server 7000，再在另一终端运行 echo_client 127.0.0.1 7000 ping。Windows 的程序文件名带 .exe。

  1. 客户端建连回调调用 trySend("ping")。4 个字节通过本地准入，随后由客户端所属线程交给其平台写路径。
  2. 服务端所属线程把到达的字节追加到 inputBuffer_，触发 setMessageCallback() 注册的函数。该示例通过 connection->trySend(buffer->retrieveAllAsString()) 消费并回送当前可读区，发送拒绝时强制关闭。
  3. 客户端消息回调消费可读区，比较收到的字符串，随后请求 shutdown()、client.stop() 和 loop.quit()。示例用一次小字符串往返演示 API。需要跨多次回调确认完整回复时，应在应用协议里定义边界。

以一笔独立的 10 KiB 发送为例，假设第一笔本地写实际处理 6 KiB。Linux 直接释放 6 KiB 额度，并缓存 4 KiB 余量等待 EPOLLOUT。Windows 收到 6 KiB 写完成后释放相同额度，保持队首段并从 6 KiB 偏移续投。最终 4 KiB 完成后，待写回到零，两种路径都可尝试安排写完成回调。

长度前缀怎样恢复消息边界

PacketFramer 是独立的协议组件。encode() 写入 4 字节网络序载荷长度，后接载荷。push() 接受任意切分的 TCP 数据，内部保存半帧，返回拥有自身存储的完整帧。一次调用也可以产出多个帧。若达到当轮预算且还有完整帧，调用方在所属线程继续 push({})。

编码后的帧   00 00 00 04  70 69 6e 67
第一次 push 00 00                       → NeedMoreData
第二次 push 00 04 70 69 6e 67           → FramesReady，载荷为 ping

把拆帧器放在连接所属线程的 context 中，可以让该连接的每次回调沿用解析状态。独立业务线程需要处理完整帧时，通过有界队列传递拥有存储的帧或命令。

协议与其他传输

拆帧、加密、RPC 和业务调度可以各自接在收发边界上。TCP 应用从连接回调接入，再沿 trySend() 回到底层。UDP、KCP 和 io_uring 有各自的运行入口与完成语义。

排查与测试

现象跟踪入口
建连回调未触发先核对 Acceptor::handleRead() / Connector::handleWrite()，再看 newConnection() 的准入、所属线程和 connectEstablished()。
已连接，消息回调无数据看 handleRead() 的输入余量和读反压。Linux 核对 Channel 兴趣及 readv() 返回值。Windows 核对 startRead()、完成通知的观察者身份及 completeRead()。
发送被拒或积压先读 trySend() 的具体结果、outputMemorySnapshot() 和 EventLoop 队列状态。Linux 跟 EPOLLOUT 和输出读索引，Windows 跟 startWrite()、已提交字节和队首 offset。
写出后没有通知看是否配置 WriteCompleteCallback，再查 queueWriteComplete() 入队结果和 droppedNotificationCount()。应用交付问题继续从对端的协议解析或响应路径定位。
关闭一直未收敛半关闭阶段先看 pendingOutputBytes()、是否尚有跨线程任务和写兴趣。Windows 再查 closePhase() 与待消费完成通知，区分已关闭 socket 与已清理连接。
